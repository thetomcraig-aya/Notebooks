# `validate_historical_data.py`

## Overview

This script performs validation checks on historical census data files. It analyzes schema consistency, date/hour coverage, volume integrity, and data quality issues, and produces a summary of findings.

---

## Required Packages

* `pandas`
* `os`
* `sys`
* `datetime`

---

## Configuration Parameters

| Parameter          | Description                                                       |
| ------------------ | ----------------------------------------------------------------- |
| `BASE_DIR`         | Directory for the project files                                   |
| `CLIENT`           | Environment variable `WFAI_CLIENT` (default: `"Wellspan"`)        |
| `HISTORICAL_DIR`   | Historical data directory within `BASE_DIR`                       |
| `HIST_FILE_FILTER` | Environment variable `WFAI_HIST_FILTER` (default: `"Historical"`) |
| `EXPECTED_COLUMNS` | List of expected column names in the CSV file                     |

---

Returns a list of `.csv` files in a given directory if the path exists.

### `print_header`

Prints a formatted subheader separator for logging.

## Main Function Workflow

### 1. Initial Setup

* Generate a list of files in the historical directory.
* Filter files based on `HIST_FILE_FILTER`.
* Select the first matching file as the working dataset.
* Load the CSV file into a pandas DataFrame.
* Initialize an empty `issues` list.

---

### 2. Schema Validation

* Print total rows, columns, and column names.
* Identify:

  * Missing columns (not in dataset but expected)
  * Extra columns (present but not expected)

---

### 3. Date / Hour Coverage

#### Date Handling

* Convert `VolDate` to datetime.

* Identify valid (non-null) dates.

* Count unparsed date values.

* Compute:

  * Minimum date
  * Maximum date
  * Date range
  * Number of unique dates
  * Number of missing dates

* Log unparsed dates as issues if any exist.

#### Hour Coverage

* Analyze `VolHour` for:

  * Earliest date
  * Latest date
* Identify partial days (< 24 hours).
* Validate hour values:

  * Must be between `0` and `23`

---

### 4. Volume Statistics

* Compute summary statistics on volume data.
* Detect:

  * Negative volume values
  * Missing volume values
* Flag data quality issues.

---

### 5. Content Breakdown

* Count rows by:

  * `Record Type`
  * `Facility`
* Calculate number of unique units.

---

### 6. Per Type and Per Unit Coverage

For each `(Type, Unit)` combination:

* Calculate:

  * Minimum date
  * Maximum date
* Generate expected full date range.
* Compare expected vs actual dates.

#### Metrics Computed

* Number of days between min and max dates
* Number of missing days
* Number of missing hours (based on `VolHour`)
* Sample of missing dates

#### Output

* Print:

  * Type
  * Unit
  * Min/Max dates
  * Missing days/hours
* Add combinations with missing dates to the `issues` list.

---

### 7. Duplicates and Key Integrity

* Check for null values in expected columns.

* Identify:

  * Duplicate records
  * Duplicate keys across:

    * `Type`
    * `Unit`
    * `VolDate`
    * `VolHour`

* Aggregate duplicate key counts by Unit.

* Print top 5 Units with highest duplicate counts.

---

### 8. Summary

* If issues exist:

  * Print all collected issues.
* Otherwise:

  * Print success message indicating validation passed.

---

## Output

* Console-based validation report
* Issue tracking via `issues` list
* Summary of data quality and completeness

## Detailed Code Walkthrough (This review is generated by Codex)

### Script Purpose

`validate_historical_data.py` validates a historical workload CSV for data quality before the data is used for onboarding, analysis, or time series forecasting preparation. The validator is intentionally self-contained: it checks the file on its own terms and does not perform lookup-table matching against external facility, unit, or type reference data.

The script is report-oriented. It prints findings to the console and builds an internal `issues` list that is summarized at the end of the run.

---

### Expected Dataset Shape

The validator expects the CSV to contain these columns:

| Column | Expected Meaning |
| --- | --- |
| `Type` | Workload or record type, such as census. |
| `Facility` | Facility associated with the unit. |
| `Unit` | Operational unit associated with the workload value. |
| `VolDate` | Date for the workload observation. |
| `VolHour` | Hour of day for the observation, expected to be `0` through `23`. |
| `Volume` | Workload value for the given type, unit, date, and hour. |

The script treats `Type + Unit + VolDate + VolHour` as the main uniqueness key when checking duplicate time-series records.

---

### Configuration and File Selection

The script builds its input path from environment variables and fixed folder conventions:

* `CLIENT` comes from `WFAI_CLIENT`, defaulting to `Wellspan`.
* `HIST_FILE_FILTER` comes from `WFAI_HIST_FILTER`, defaulting to `Historical`.
* `HISTORICAL_DIR` is built as `BASE_DIR/data/<CLIENT>/Historical`.

`BASE_DIR` is calculated as:

```python
os.path.dirname(os.path.dirname(os.path.abspath(__file__)))
```

That means the script expects to live one folder below the project base, such as a `script` folder. If it is run from the workspace root, `BASE_DIR` resolves one level above the current folder.

File selection works as follows:

1. `find_csv_files()` lists all `.csv` files in `HISTORICAL_DIR`.
2. If no CSV files are found, the script prints an error and exits with status code `1`.
3. If `HIST_FILE_FILTER` is set, the script looks for CSV filenames containing that filter text.
4. If filtered matches exist, only those files are considered.
5. The script selects the first file in the resulting list.

The selected file is not explicitly sorted, so the "first" file depends on the order returned by `os.listdir()`.

### CSV Loading

The CSV is loaded with pandas:

```python
pd.read_csv(hist_path, sep=None, engine="python", encoding="utf-8-sig")
```

Important behavior:

* `sep=None` lets pandas infer the delimiter.
* `engine="python"` is required for delimiter inference.
* `encoding="utf-8-sig"` supports CSV files that include a UTF-8 byte order mark.

After loading, the script initializes:

```python
issues = []
```

This list is the central collection point for flagged validation problems.

---

### Section 1: Schema Validation

The schema section prints basic shape information:

* Total rows
* Total columns
* Column names

Then it compares the actual DataFrame columns to `EXPECTED_COLUMNS`.

It identifies:

* Missing expected columns
* Extra unexpected columns

Missing columns are flagged and added to `issues`. Extra columns are informational only and do not cause the final status to fail.

---

### Section 2: Date and Hour Coverage

The script converts `VolDate` into a temporary datetime column named `_d`:

```python
df["_d"] = pd.to_datetime(df["VolDate"], format="mixed", errors="coerce")
```

Unparseable date values become null datetime values. The script then computes:

* Earliest valid date
* Latest valid date
* Inclusive date span
* Approximate month span
* Number of unique dates
* Missing calendar days across the full dataset
* Count of unparseable date values

Unparseable dates are flagged and added to `issues`.

The script also checks boundary-day truncation:

* It finds the hours present on the first date.
* It finds the hours present on the last date.
* If either date has fewer than 24 hours, it prints an informational message.

This is useful because historical extracts often begin or end mid-day. The script treats this as informational rather than automatically invalid.

Finally, the script validates `VolHour`:

* It prints the observed hour range.
* It counts rows where `VolHour` is less than `0` or greater than `23`.
* Invalid hours are flagged and added to `issues`.

---

### Section 3: Volume Statistics

If the `Volume` column exists, the script calculates:

* Minimum volume
* Maximum volume
* Mean volume
* Median volume
* Null count
* Zero count
* Zero percentage
* Negative value count

Negative values are flagged because workload volume should generally not be below zero. Null values are also flagged because missing target values can break downstream analysis or model training.

Zero values are reported but not automatically treated as invalid. This is reasonable because some units or workload types may legitimately have zero volume during certain hours.

---

### Section 4: Content Breakdown

The content breakdown section gives a high-level view of what is inside the file.

It prints:

* Row counts by `Type`
* Row counts by `Facility`
* Number of unique `Unit` values

This section helps reviewers quickly spot unexpected record types, facilities with unusually high or low volume of rows, or a surprising unit count.

The section is descriptive only. It does not add anything to `issues`.

---

### Section 5: Per-`(Type, Unit)` Coverage and Gaps

This is the most time-series-specific part of the validator.

The script groups the dataset by:

```text
Type + Unit
```

For each group, it calculates:

* Minimum date
* Maximum date
* Inclusive day span
* Expected daily date range between min and max
* Actual dates present
* Missing calendar days
* Missing hourly slots
* Row count
* Up to five sample missing dates

Missing calendar days are calculated by comparing the expected date range to the actual dates present in the group.

Missing hourly slots are estimated by counting distinct `VolHour` values per date, then summing the difference from 24:

```text
missing hours = sum(24 - distinct hours present for each date)
```

The script prints a fixed-width summary table for every `(Type, Unit)` pair. Long unit names are truncated to 55 characters so the report remains readable in the console.

After the table, the script identifies all groups with missing calendar days. If any exist, it prints a separate subsection with details and sample missing dates. It also adds a single issue summarizing how many `(Type, Unit)` combinations have missing calendar-day gaps.

---

### Section 6: Duplicates and Key Integrity

This section checks whether rows are complete and uniquely identifiable.

First, the script checks null counts for every expected column that exists in the DataFrame:

* `Type`
* `Facility`
* `Unit`
* `VolDate`
* `VolHour`
* `Volume`

Any null count greater than zero is flagged and added to `issues`.

Next, it checks full-row duplicates with:

```python
df.duplicated().sum()
```

Full-row duplicates are flagged and added to `issues`.

Finally, it checks duplicate logical keys using:

```text
Type + Unit + VolDate + VolHour
```

Duplicate keys are important because a forecasting dataset generally needs one target value per series and timestamp. If multiple rows share the same key, the model pipeline would need a rule for aggregation, deduplication, or rejection.

When duplicate keys are found, the script:

* Prints the duplicate count.
* Adds a duplicate-key issue to `issues`.
* Groups affected duplicate rows by `Unit`.
* Prints the top five units with the most duplicate-key rows.

The issue message notes that duplicate keys may suggest sub-locations rolled up under one shared unit string.

---

### Section 7: Final Summary

At the end of the report, the script checks whether `issues` contains any entries.

If issues exist, it prints:

```text
Status: FLAG
```

Then it prints every issue as a numbered list.

If no issues exist, it prints:

```text
Status: PASS
```

After printing the final report footer, the script removes the temporary `_d` column from the DataFrame if it exists.

## What Gets Added to `issues`

The following conditions affect the final `FLAG` or `PASS` status:

* Missing expected columns
* Unparseable date values
* `VolHour` values outside `0` through `23`
* Negative `Volume` values
* Null `Volume` values
* Missing calendar days in one or more `(Type, Unit)` groups
* Null values in expected columns
* Full-row duplicates
* Duplicate `Type + Unit + VolDate + VolHour` keys

The following are reported but do not currently affect final status:

* Extra columns
* Partial first day
* Partial last day
* Zero volume values
* Content distribution by type
* Content distribution by facility
* Number of unique units
* Global calendar gap count by itself

## Forecasting-Relevant Interpretation

For time series forecasting, the most important validations in this script are:

* Hour range validation, because hourly models require valid timestamp components.
* Per-`(Type, Unit)` missing day and missing hour checks, because each series needs regular observations.
* Duplicate key checks, because a model should generally receive one value per series per timestamp.
* Null and negative volume checks, because `Volume` is the target variable.
* Date span reporting, because short histories may not contain enough seasonal signal.

The script is a strong first-pass data quality report, but it does not yet fully determine whether a dataset is model-ready. It does not enforce minimum history length, validate recent-window completeness, detect outliers, detect flatlines, construct a true timestamp column, or check for distribution drift.

---

## Current Assumptions and Limitations

* The script assumes `VolDate` exists before it attempts date parsing.
* The script assumes `Type` and `Unit` exist before the per-series groupby step.
* Boundary-day checks assume usable `VolHour` values exist for the first and last parsed dates.
* Only one CSV file is validated per run.
* File selection is not deterministic unless the source directory contains only one matching file.
* `Facility` is not part of the duplicate-key check.
* `Volume` is not explicitly coerced to numeric before statistics are calculated.
* The script prints a console report but does not save machine-readable validation output.
* The final result is based on accumulated issue strings rather than structured severity levels.

---

## Suggested Enhancements

Good next improvements would be:

* Build a true hourly timestamp from `VolDate` and `VolHour`.
* Sort files before selecting the first matching CSV.
* Allow the input file path to be passed as a command-line argument.
* Add severity levels such as `ERROR`, `WARN`, and `INFO`.
* Save the validation result as JSON or CSV.
* Include `Facility` in the series identifier or explicitly validate `Unit` to `Facility` consistency.
* Enforce minimum history length per forecasted series.
* Check completeness for recent windows such as the last 7, 14, 30, and 90 days.
* Detect longest contiguous gaps.
* Detect extreme outliers, sudden spikes, sudden drops, and long flatlines.
* Validate that no dates occur after the expected extract cutoff.
* Normalize string columns by trimming whitespace and checking casing differences.
